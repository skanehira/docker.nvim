## 1. 適用範囲

docker.nvim は利用者の Neovim 内で動作するプラグインであり、サーバー・クラウドリソース・デプロイ先を持たない。したがって一般的なインフラ詳細設計の項目の多くは該当しない。本書が扱うのは次の 2 つに限られる。

| 扱う | 扱わない（該当なし） |
| --- | --- |
| GitHub Actions による CI | クラウドリソース定義、IaC、ネットワーク設計 |
| プラグインマネージャ経由の配布 | デプロイパイプライン、環境ごとの構成、GitHub Environments |
| リポジトリの設定（ブランチ保護など） | データストア運用、バックアップ、監視基盤、シークレット管理 |

**該当なしとする項目とその理由**:

| 項目 | 理由 |
| --- | --- |
| インフラ構成図・リソース定義 | 常時稼働するリソースが存在しない（実行環境は利用者の Neovim プロセスのみ） |
| IaC（Terraform 等） | 管理対象のリソースが無い |
| デプロイフロー・環境の面数 | デプロイという行為が無い。利用者がリポジトリを取得した時点が「配布」の完了 |
| データストア運用・バックアップ | 永続データを持たない（[DESIGN_DETAIL_APP.md の 4. データ構造](DESIGN_DETAIL_APP.md#4-データ構造)） |
| 監視・アラート | 稼働を監視すべきサービスが無い |
| シークレット管理 | CI で外部サービスの認証情報を使わない |
| スケーリング・可用性（SLO / RTO / RPO） | 単一利用者のローカルプロセスであり、可用性の概念が適用されない |

## 2. 配布とインストール

### 2.1 配布方法

GitHub リポジトリをプラグインマネージャが直接取得する。パッケージレジストリへの公開やリリース成果物のビルドは行わない（Lua のためビルド成果物が存在しない）。

利用者側の記述例（lazy.nvim）:

```lua
{
  "skanehira/docker.nvim",
  cmd = "Docker",
  opts = {},
}
```

`opts` を渡すと `require("docker").setup(opts)` が呼ばれる。設定なしでもデフォルトのキーマップで動作する。

### 2.2 バージョニング

| 項目 | 方針 |
| --- | --- |
| タグ | セマンティックバージョニングのタグ（`v0.1.0` 形式）を付ける |
| 破壊的変更 | 設定キーの改名・削除、デフォルトキーマップの変更を破壊的変更として扱い、マイナーバージョンを上げる（1.0 到達までは） |
| 変更履歴 | リリースノートに記載する。専用の変更履歴ファイルは持たない |

### 2.3 利用者側の前提

利用者環境に求める前提を宣言する。いずれの確認処理もプラグイン内の振る舞いであり、仕様は [DESIGN_DETAIL_APP.md の 8.1 エラーの分類と扱い](DESIGN_DETAIL_APP.md#81-エラーの分類と扱い) に置く。

| 前提 | 満たさない場合 |
| --- | --- |
| Neovim 0.10 以上 | `setup()` の時点で機能を無効化し、対応バージョンを通知する |
| `docker` コマンドが PATH 上にある | 一覧を開く操作でメッセージを表示し、ビューを開かない |
| `docker compose` サブコマンドが使える | サービス一覧のみ利用できない。他のリソースのビューは動作する |

## 3. CI/CD パイプライン

CD（デプロイ）は存在しないため、パイプラインは CI のみで構成する。

### 3.1 workflow 一覧

| ファイル | トリガー | ジョブ |
| --- | --- | --- |
| `.github/workflows/ci.yml` | `push`（デフォルトブランチ）、`pull_request` | `test` / `lint` / `format` / `typecheck` / `e2e` |

各ジョブは互いに独立で並列に実行する。

### 3.2 ジョブ定義

| ジョブ | 実行環境 | 内容 | 失敗の扱い |
| --- | --- | --- | --- |
| `test` | `ubuntu-latest`、Neovim 0.10.0 と stable のマトリクス | plenary.nvim を取得し `make spec-layout-check` / `make plugin-check` / `make test` を実行する | 必須。失敗でマージ不可 |
| `lint` | `ubuntu-latest` | `make lint`（luacheck） | 必須 |
| `format` | `ubuntu-latest` | stylua-action で `--check lua/ plugin/ tests/`（ローカルの `make format-check` と同等） | 必須 |
| `typecheck` | `ubuntu-latest` | `make typecheck`（lua-language-server） | 必須 |
| `e2e` | `ubuntu-latest`（ランナー同梱の docker を使用） | `make test-e2e`（`scripts/e2e.sh`）。実際の docker デーモンに対する G_E2E の通し確認 | 必須 |

補足:

- Neovim のバージョン固定に `0.10.0` を含めるのは、[DESIGN.md の制約](DESIGN.md#17-制約と前提)で下限を 0.10 としているため。stable との 2 本立てで、下限と最新の両方の互換を守る
- `e2e` ジョブは GitHub ホストランナーに同梱されている docker を使う。追加のサービスコンテナ設定は不要
- macOS ランナーでの実行は行わない。docker が同梱されておらず、実行時間とコストに見合わないため。macOS での動作は開発者のローカルで `make test-e2e` を実行して確認する
- テストの依存（plenary.nvim）は各ジョブで取得する。プラグインマネージャは CI では使わない
- **判定を下す道具はすべて版を固定する**。アクションを SHA で固定しても、実際に緑赤を決める道具（plenary.nvim・luacheck・StyLua・lua-language-server・検証用の docker イメージ）が浮動していれば、コードを変えていないのに CI の結果が変わって原因を追えなくなる。固定値はワークフロー冒頭の `env` に集約し、1 箇所で見渡せるようにする。StyLua は開発環境と同じ版に揃え、ローカルで通る整形が CI で落ちないようにする

### 3.3 リポジトリ設定

| 項目 | 設定 |
| --- | --- |
| デフォルトブランチ | `main` |
| ブランチ保護 | `main` への直接プッシュを禁止し、プルリクエストと CI の全ジョブ成功を必須にする |
| GitHub Environments | 該当なし（デプロイ先が無いため） |
| 承認ステップ | 該当なし（単一開発者のため。将来コントリビュータが増えた時点で見直す） |
| アクションの版管理 | `uses:` はコミット SHA で固定し、末尾に `# vX.Y.Z` を書く。更新は dependabot（`package-ecosystem: github-actions`、週次）に任せる。メジャー更新は SHA 固定と別コミットにする |

アクションの版管理の補足:

- 浮動タグ（`@v4` 等）はタグの付け替えで参照先が変わる。同じコミットに対して CI の結果が変わりうるため、SHA で固定する
- 固定したままでは脆弱性修正が届かないので、更新経路として `.github/dependabot.yml` を置く。固定と自動更新はセットで初めて意味を持つ
- 「SHA へ固定する」変更と「バージョンを上げる」変更を 1 コミットに混ぜない。CI が落ちたときにどちらが原因か切り分けられなくなる

### 3.4 ロールバック

デプロイが無いため、ロールバックはリポジトリの操作のみで完結する。問題のあるコミットが `main` に入った場合は、該当コミットを打ち消すコミットを積むか、直前のタグを利用者に案内する。

## 4. シークレット・環境変数管理

### 4.1 CI のシークレット

該当なし。CI で外部サービスへ接続しないため、`secrets` を使用しない（`GITHUB_TOKEN` の既定の権限のみで動作する）。

### 4.2 プラグインが参照する環境変数

プラグイン自身は環境変数を読まない。docker の接続先の解決はすべて docker CLI に委ねる（これが CLI 経由を選んだ理由の 1 つ。[DESIGN.md の 1.6](DESIGN.md#16-検討した代替案)）。結果として、利用者が設定した次の環境変数は docker CLI を通じて自動的に効く。

| 環境変数 | 効果 | 誰が解釈するか |
| --- | --- | --- |
| `DOCKER_HOST` | 接続先デーモンの指定 | docker CLI |
| `DOCKER_CONTEXT` | docker context の選択 | docker CLI |
| `COMPOSE_PROJECT_NAME` | compose プロジェクト名の上書き | docker compose CLI |
| `COMPOSE_FILE` | compose ファイルの指定 | docker compose CLI |

プラグインはこれらを自前で解釈しない（BR-004）。

## 5. 監視・アラート

該当なし。常時稼働するサービスを持たないため、収集すべきメトリクスもアラート閾値も存在しない。

不具合の検知経路は次のとおり。

| 経路 | 内容 |
| --- | --- |
| CI | プルリクエストごとの全ジョブ実行で回帰を検知する |
| 利用者からの報告 | GitHub Issue |
| デバッグログ | 利用者が `setup({ debug = true })` を有効にしたときのみ出力される。報告時に添付してもらう |

## 6. スケーリング・可用性・コスト

| 項目 | 内容 |
| --- | --- |
| スケーリング | 該当なし（単一プロセス内で動作し、負荷に応じた増減の概念が無い） |
| 可用性・障害復旧（RTO / RPO） | 該当なし（永続データもサービスも持たない） |
| コスト | GitHub Actions の無料枠内で完結する。パブリックリポジトリのため実行時間の課金は発生しない |
| 性能上の制約 | 利用者環境のコンテナ数に依存する。目標値は [DESIGN.md の 2.4](DESIGN.md#24-非機能要件アプリ側) を参照 |

## 7. 検証手順

インフラ側で検証するのは CI の設定そのものである。ゴール G1〜G13 および G_E2E の検証手順は、すべてローカルと CI で実行できるため [DESIGN_DETAIL_APP.md の 9. 検証手順](DESIGN_DETAIL_APP.md#9-検証手順) に置く。

- CI-1 検証: プルリクエストを作成し、`test` / `lint` / `format` / `typecheck` / `e2e` の 5 ジョブがすべて実行され成功すること（GitHub の Checks 画面で確認）
- CI-2 検証: `test` ジョブが Neovim 0.10.0 と stable の 2 通りで実行されていること（マトリクスの展開を Checks 画面で確認）
- CI-3 検証: 意図的にテストを失敗させたコミットで、`main` へのマージがブロックされること（ブランチ保護の動作確認、初回設定時に 1 度だけ実施）
- CI-4 検証 (手動): `.github/workflows/ci.yml` に `secrets` の参照が無いことを確認する（`rg 'secrets\.' .github/workflows/` が `GITHUB_TOKEN` 以外を返さないこと）
- CI-5 検証 (手動): 全ての `uses:` が 40 桁のコミット SHA で固定されていることを確認する（`rg -c 'uses: ' .github/workflows/ci.yml` と `rg -c 'uses: [^@]+@[0-9a-f]{40} # ' .github/workflows/ci.yml` の件数が一致すること）
